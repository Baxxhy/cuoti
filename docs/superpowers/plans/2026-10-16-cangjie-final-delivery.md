| 验证 | 上轮 `make verify`通过的是Python主线；仓颉主要是原生/HTTP测试 | 缺最终架构浏览器、真实模型和学生使用验收 |
| 文档 | 旧完成矩阵和迁移文档摘要有历史数字 | 保留历史证据，新增唯一最终验收矩阵，避免互相矛盾 |

## 二、分期原则与依赖

执行顺序：P0基线 → P1运行骨架 → P2既有接口补齐 → P3检索与数据 → P4完整学习闭环 → P5新增订正/自检 → P6学生体验 → P7全角色集成 → P8真实能力验证 → P9最终交付。

P2、P3有明确依赖的部分交替推进：练习接口先完成协议和可用候选查询，再接检索重排。P4不能靠模拟数据跨过P2/P3。每阶段完成后记录证据并提交相关文件；任何阶段不通过，先修复再进入依赖它的阶段。

不默认并行委派；保留当前其他工作的改动，不使用全目录暂存、重置或清理来获得表面“干净”。方案阶段与实施阶段分开记录，不能把计划中的功能写成已经完成。

## 四、验收分层与命令

| 层级 | 使用现有或新增入口 | 证明什么 |
| --- | --- | --- |
| 原仓颉回归 | `make verify-cangjie` | 原生行为、隔离MySQL、算法协议与HTTP；要同步接入新模块测试 |
| 算法单元 | `.venv/bin/python -m pytest backend-algorithms/tests`（按现有脚本配置PYTHONPATH） | 纯计算、Pydantic、错误映射、不依赖业务数据库 |
| 前端 | `npm --prefix frontend test`、`run typecheck`、`run build:h5` | 页面状态、类型、构建 |
| 最终浏览器 | 新增仓颉专用Playwright入口 | 页面实际访问仓颉，不默默复用旧业务服务 |
| 最终完整验收 | 新增 `make verify-final` | 三端完整集成及数据恢复；定义落实后才声称命令存在 |
| 真实能力 | 新增/适配明确的仓颉真实AI/语音验证入口 | 模拟测试不能覆盖的实际模型与引擎表现 |
| 学生任务 | 试用记录模板与实际观察 | “适合中学生”是否得到实际证据 |

保留 `make verify` 对旧版的兼容检查价值，但它不能替代最终架构验收。测试只在改动、新失败或新风险时扩展；不为达到数字而重复添加源码字符串断言。

## 五、实施中的重点决策

1. **并行工作**：系统/语音/管理正在改，先核验其最终状态；不抢改相同文件或把别人的未完成代码当稳定基线。
2. **数据准备**：知识卡与题库缺失会让页面“能打开但不可用”，必须作为主任务验收；不直接连接旧生产库掩盖问题。
3. **检索职责**：业务候选和事实在仓颉/MySQL，检索排序在Python；索引不能绕过业务可用性与年级限制。
4. **新功能**：订正与自检需要明确持久化和证据资格；实现成本不能通过覆盖原作答或前端localStorage规避。
5. **界面与算法**：先接真实闭环，再优化层级；不能用界面显示“完成”补偿后端缺失。
6. **发布范围**：这版是完整本地交付，不额外建设商业云平台。真实用户数据迁入与对外部署不作为整理功能的隐含操作。
