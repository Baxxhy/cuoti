# 错题帮高层架构与图表设计清单

审查日期：2026-10-18。审查范围：当前源码、`docs/ARCHITECTURE.md`、任务与手机交付工程。本文是统一写作和图表渲染的设计依据，不是正式项目说明正文。图源位于同级 `figures/`，共 16 份 Mermaid 文件；主编排 Agent 统一渲染、排版与终审。

## 1. 唯一可信架构基线

**当前主线是一个仓颉业务服务，协作一个 Python/FastAPI 内部算法服务。** 仓颉集中处理身份权限、题目与作答、学习任务、业务状态、MySQL 事务和受控文件。Python 接收受认证的计算契约，返回结构化结果、证据和建议，不拥有业务数据库或学生账号状态。题库的事实数据位于 MySQL，Qdrant 是检索索引，BGE 提供嵌入/重排；算法服务经 ApiPoolProvider 使用逻辑模型 Qwen。

前端是 uni-app、Vue 3、TypeScript 和 uni-ui。当前验证可以支持 H5 运行与 App 本地资源构建的表述。Android/iOS 签名、安装、真机和发行必须放在未来交付路线，不能用“跨端工程”替代这些成果。

智能体采用**持久任务协调器与有界工具计算**：仓颉拥有任务与提交权限，Python 执行观察、规划、工具和验证；学生实际动作驱动下一轮。源题/作答/诊断/知识及记忆来源被版本化核对，迟到、取消和过期结果不能直接更新学习记录。不要把工具名分别画成自治 Agent，也不要引入消息队列、Redis、Kubernetes、对象存储或独立“掌握度微服务”等当前不存在的运行单元。

| 图中统一名称 | 对应真实实现 | 画图要求 |
| --- | --- | --- |
| 移动交互层 | `frontend/src/` | 当前 H5 与 App 资源基础；手机签名包单独标规划 |
| 仓颉业务服务 | `backend-cangjie/src/` | 内部模块可以分区，但进程边界只画一个业务服务 |
| Python 算法服务 | `backend-algorithms/service.py` 与各计算模块 | 内部计算边界，不接入主线业务数据库 |
| MySQL | `backend-cangjie/schema/` | 唯一业务数据库，保存事实和状态 |
| 文件存储 | `media_storage.cj`、`recognition_worker.cj` 等 | 当前本地文件；原图与派生文件分开 |
| 检索组件 | `retrieval.cj`、`retrieval_compute.py` | 索引召回后回 MySQL 核对来源与可用性 |
| 模型能力 | `backend/app/providers/api_pool.py` | ApiPoolProvider 轮询，逻辑模型 Qwen；不画私有端点 |
| 规则与验证 | `diagnosis_compute.py`、`grading_compute.py`、`learning_task_compute.py` | 不把模型解释标成数学证明 |

## 2. 通用视觉与语义规范

- 白底、深蓝主色 `#173B63`、青绿强调 `#168C89`、浅灰分区 `#F3F6FA`；规划区用虚线和“规划”文字双重区分。
- 采用中文标题和节点名称。技术栈、状态枚举和代码表名可作为小号副标签；正文首次定义。
- 实线箭头表示调用或控制；带说明的细实线表示数据结果；虚线表示约束、引用或未来依赖。箭头必须有业务含义，不能只用颜色表达。
- 每张图应有一条核心结论。纵向架构图 4–5 层以内，流程图优先左至右；超过 8 个主要节点时使用分组或两列，不压缩字体。
- A4 正文图区建议宽 155–165 mm，最终中文标注至少 9 pt；状态图、ER 图建议整页。导出 SVG 保留可编辑文字，并输出 2–3 倍 PNG 供 Word 使用。
- 图中的源码路径不放在节点里，置于图下注或证据表；图中文字解释架构，正文解释设计理由。
- 原始 `.mmd` 是语义图源。Graphviz/SVG 渲染时可调整位置和样式，不能改变关系、门槛或当前/规划状态。目录中的图号为全局编号，正式两份文档可按章生成最终图号。

## 4. 逐图设计与证据

### 图 01：产品与学习闭环总览

**核心结论：** 错题录入只是起点，产品通过可追溯诊断、修复、验证与复习形成持续学习闭环。

节点与关系：原题和原作答 → 证据诊断 → 错因回放与易错地图 → 修复任务 → 支持时的条件对照 → 学习记录与复习；记录再影响下一步任务。用户任务、证据与反馈三个层次分别用上方旅程、中央主要动作、下方反馈箭头表达。

结构建议：Graphviz `rankdir=LR`，六个主节点同一层；回环箭头从底部返回地图/任务，避免穿过节点。项目说明“总体方案”使用，先解释“为什么做”，不展开接口。

代码依据：`frontend/src/pages/index/index.vue`、`pages/diagnosis/diagnosis.vue`、`pages/repair/repair.vue`、`pages/task/task.vue`；`backend-cangjie/src/learning_task_worker.cj`、`reviews.cj`、`cognition_graph.cj`。

范围边界：不是所有正确订正都增加知识掌握，不是所有题都生成单条件对照。图中“支持时”不能省略。

### 图 02：系统上下文

**核心结论：** 学生是核心用户，教师、家长和管理员在各自授权范围协作，外部模型与题库提供能力和内容。

节点与关系：四类用户围绕一个系统边界；外部 Qwen 是模型提供方；题库资料经管理命令导入。不要把 MySQL、仓颉、Python 详细展开，本图只解释系统与环境。

结构建议：中央系统大矩形，左侧学生置顶；其余角色上下排列，外部依赖在右侧。用于项目说明“用户与场景”。

代码依据：`backend-cangjie/src/auth.cj`、`school_access.cj`、`guardian_links.cj`、`admin_api.cj`、`question_bank_cli.cj`；`backend/app/providers/api_pool.py`。

范围边界：角色页面已存在，不能将其描述成学校大规模 SaaS 已部署；导入题库不等于实时联网爬题。

### 图 03：整体分层架构

**核心结论：** 交互、业务事实、智能计算和数据依赖的责任分离，模型输出通过业务层受控落地。

节点与关系：交互层向仓颉发送业务请求；仓颉事务读写 MySQL、管理媒体并调用内部 Python；Python 调模型、检索和规则，返回结构化结果。算法不直接向 MySQL 写学生状态。

结构建议：Graphviz 纵向 `rankdir=TB`；每层以浅色横条容器呈现。数据层和外部能力可在底层并列。用于项目说明“技术概览”。

代码依据：`frontend/src/api/index.js`、`backend-cangjie/src/router.cj`、`algorithm_client.cj`、`database.cj`、`backend-algorithms/service.py`、`docs/ARCHITECTURE.md`。

范围边界：文件名只作来源入口，不在正文逐文件解释；Python 复用 `backend/app/services/` 的算法代码不表示旧 Python 业务服务回到主线。

### 图 04：C4 容器架构

**核心结论：** 前端、仓颉、内部算法及数据依赖是有明确通信边界的运行单元，业务内部模块不另立微服务。

节点与关系：前端 → 仓颉 → MySQL/本地文件/Python；Python → BGE/Qdrant/模型池。仓颉框内标注包含 worker，算法框内标注 FastAPI。系统边界包围自有组件，外部 Qwen 在边界外。

结构建议：Graphviz cluster 表示系统边界，节点形状区分应用、存储、外部服务；容器下方写技术栈与简短职责。用于系统设计“总体架构”。

代码依据：`scripts/final.sh`、`scripts/algorithms.sh`、`scripts/cangjie.sh`、`backend-algorithms/service.py`、`backend-algorithms/retrieval_compute.py`、`backend-cangjie/src/retrieval.cj`。

范围边界：这里的 container 指 C4 的应用/数据运行单元，不声明使用 Docker；当前没有消息中间件要求。

### 图 05：核心模块职责与依赖

**核心结论：** 围绕学习事实组织模块，而不是围绕模型名字组织系统。

节点与关系：身份权限约束题目、任务与班级；题目→诊断→任务→证据/掌握→复习；诊断与学习记录投影到地图和报告；题库支持专项练习；教师复核与学习证据相连。

结构建议：仓颉业务模块置于一个大 cluster；智能计算契约置在框外。实线依赖、虚线权限约束。用于系统设计“模块职责”，配合职责矩阵。

代码依据：`manual_questions.cj`、`diagnosis_api.cj`、`learning_tasks.cj`、`learning_evidence.cj`、`practice_attempt.cj`、`reviews.cj`、`cognition_graph.cj`、`assignment_reviews.cj`。

范围边界：图中模块是内部职责分区，不是八个网络服务，也不意味着模块可单独部署。

### 图 06：错题采集与结构化处理

**核心结论：** 采集既保留原材料，也给学生校正识别结果的机会，避免把 OCR 错误直接变成学习诊断。

节点与关系：相机/相册 → 原图保存 → 裁剪/预处理 → 结构识别 → 学生校对；手动入口合流到校对；校对后保存题目与作答，再启动分析。原图与派生图分别存放。

结构建议：主链在中央一行，手动入口从上方合流；原图资产和派生图用下方细线表示。用于项目说明“核心场景”。

代码依据：`frontend/src/pages/capture/`、`pages/crop/`、`pages/detail/detail.vue`（识别结果校对与作答维护入口）；`ingest_api.cj`、`crop_api.cj`、`recognition_api.cj`、`recognition_worker.cj`；`backend-algorithms/service.py`。

范围边界：这里是产品流程，不宣称识别全题型无误；原图不被清洁图覆盖。实际手机相机/相册体验仍需真机验收。

### 图 07：错误诊断与证据传递

**核心结论：** 一条诊断必须能关联学生实际作答与证据范围，模型候选和规则验证分别表达。

节点与关系：原题、学生步骤 ID、参考步骤 ID → 输入快照 → 语义候选 → 范围内规则核验 → 首错/作用域/验证状态 → 业务层核对来源 ID 和版本 → 诊断证据保存 → 回放/地图。

结构建议：Graphviz 左端三类输入并列，中间流水线，输出端“已核验/待核对”使用双色状态标签。用于系统设计“诊断与证据”。

代码依据：`backend-cangjie/src/diagnosis_api.cj` 的 `diagnosisSnapshot`、`saveDiagnosticEvidence`；`backend-algorithms/diagnosis_compute.py`、`diagnosis_alignment.py`；`backend/app/services/ai_pipeline.py`；`backend-cangjie/schema/001_initial.sql` 的诊断证据外键。

范围边界：不同解法不能按参考行号机械判错；无参考映射可为 null；不支持的语义诊断保留 `model_review_requires_confirmation`，不画成 SymPy 已证明。

### 图 08：智能体任务执行时序

**核心结论：** 模型负责建议与计算，仓颉在学生动作和持久事务的约束下控制任务执行。

参与者：学生/前端、仓颉协调器、MySQL、Python 策略工具。步骤为受理动作 → 保存并返回 → worker 领取 → 计算 → 再验证并提交 → 查询公开视图。计算期间不持有跨网络长事务。

结构建议：四泳道顺序固定；受理响应与异步 worker 之间留明显间隔。Python 自调用框“观察/规划/工具/验证”可高亮，不拆成四个 Agent。用于系统设计“智能体机制”。

代码依据：`learning_tasks.cj`、`learning_task_worker.cj`、`learning_task_budget.cj`、`learning_task_sources.cj`、`learning_memory_sources.cj`；`backend-algorithms/learning_task_compute.py`。

范围边界：提交前还要比对重新读取的上下文，不仅验租约。学生公开视图不包含私有答案、完整检查点或租约。

### 图 09：学习任务生命周期

**核心结论：** 业务执行状态与教学阶段分开，重试、取消、失效具有明确规则。

八种状态：`queued`、`running`、`waiting_student`、`needs_review`、`completed`、`failed`、`cancelled`、`stale`。正常链是排队→运行→等待学生/待核对/完成。等待、待核对、可重试失败经合法动作重新排队。运行租约过期可重新领取。取消与来源失效阻止迟到提交。

结构建议：正常路径沿中央，failed/retry 在下方，cancelled/stale 在右侧终态区。图源列出来源变更的各前置状态，正式图可汇成“除 cancelled/stale 外、检查时发现源题变化→stale”的注释，降低交叉线。

代码依据：`learning_tasks.cj` 的 `taskValidateVersion` 与动作入口；`learning_task_worker.cj` 的领取、失败和结果白名单；`schema/006_learning_tasks.sql`。

范围边界：`completed` 后发现原题变更仍可标 stale；不是无条件自动重试 failed；`repair/independent/contrast/done` 不属于这八个业务状态。

### 图 10：订正、独立练习和条件对照

**核心结论：** 看懂或订正成功不直接等同掌握；不同学习证据按作用域逐步推进。

节点与关系：支持局部验证→repair→independent；不支持局部验证直接 independent；原题正确后，只有可构造并验证的单条件对照才进入 contrast，否则完成当前任务；有效独立、未重复曝光且可更新的 contrast 生成一次近迁移证据。任何不确定判定可进入待核对。

结构建议：四阶段横排，两个条件菱形分别控制局部修复和对照生成；“学习更新”画在下方旁支，避免 completed=掌握 的错误暗示。

代码依据：`learning_task_compute.py` 约 1000 行后的阶段推进与 `make_contrast`；`learning_task_worker.cj` 的 `eligible`、`learning_task_exposures`、`applyLearningEvidence`。

范围边界：当前任务局部符号订正和单条件对照有题型限制，主要为可独立核验的一元一次方程。其他题型原题作答流程和既有专项/迁移练习能力另行区分。

### 图 11：学习记录、掌握度与复习

**核心结论：** 掌握情况是基于有效证据的估计，复习以真实记录持续更新，自检属于学生自述。

节点与关系：路径A为符合准入的任务/专项练习结果→资格核验→认知规则计算→掌握、误区及认知更新。路径B为复习作答→复习记录与下次计划→有效记忆和学习建议。当前 `reviews.cj` 的 `gradeReview` 不调用 `applyLearningEvidence`，不能画成所有复习结果都会更新掌握估计。自检要点仅作为学生自述提醒，不连接为“客观掌握证明”。

结构建议：采用上下两条独立路径，分别表达认知更新和复习记录；底部汇入有来源的记忆与建议，不把两条写入路径合成一条。用于项目说明“持续学习价值”，机制细节在系统设计引用。

代码依据：`learning_evidence.cj`、`practice_attempt.cj`、`reviews.cj`、`learning_task_records.cj`；`backend/app/services/cognition_rules.py`；`backend-algorithms/learning_memory_compute.py`。

范围边界：不将单次正确画为知识点100%掌握；不声明已经证明长期提分效果。不能将“间隔复习”标成已采用 Anki/FSRS 算法，除非另有源码证据。

### 图 12：概念数据模型

**核心结论：** 原题、作答步骤、诊断证据、任务动作和复习记录关联保存，结果能返回来源。

节点与关系：保留用户、错题、作答及步骤、分析及参考步骤、诊断及证据、任务及冻结来源/动作/轨迹/自检、掌握估计、认知更新、复习计划/记录。图源不展开字段。

结构建议：Graphviz 三列：原材料、诊断与任务、学习与复习；ER 图保留基数。中文实体对应同义表名，真实数据类型在 schema，不塞进正文。自检与任务为至多一份逻辑要点（按用户和任务唯一），冻结来源为一任务至多一行。

### 图 15：异常恢复与失败处理

**核心结论：** 可重算只读算法，提交结果必须再次满足业务条件；可靠性来自持久状态和事务防重。
