## 1 总体设计

### 1.1 设计目标

系统设计服务于学生错题学习的连续过程：采集可信材料，分析实际作答，支持关键步骤订正，再通过独立表现与复习形成新证据。各层围绕明确职责协作，计算结果经业务校验后进入学习记录。高层设计关注模块间的关系、数据流向、状态生命周期与失败处理。前端交互、仓颉业务、Python计算和数据检索在部署上相互协作，在责任上保持明确。对学生而言任务可以中断和恢复；对维护者而言结果可以关联来源并定位到具体处理阶段。

表1  设计目标

| 设计目标 | 可观察标准 |
|---|---|
| 连续学习 | 同一题目能够进入订正、训练与复习 |
| 事实可追溯 | 结论回到原题、原作答和有效版本 |
| 运行可恢复 | 失败、重复、重启不重复写入证据 |
| 边界清晰 | 模型建议由业务规则决定是否提交 |

系统以事实集中、来源关联和提交校验组织业务。MySQL保存业务事实，仓颉负责身份、状态、来源及事务写入，Python主线返回计算结果。照片、当时作答和后续诊断分别保留，通过来源关系连接；学生纠正输入后，派生结果依据现行材料重新核对。状态推进依次核对输出结构、计算依据与业务资格。结构校验使结果可以安全消费，数学工具检查明确范围内的关系，学习更新还需要独立性和来源等证据条件。请求受理、计算完成、页面回读和学习更新各有确认点，网络中断后从已经保存的状态恢复。

当前采用一个仓颉业务进程与一个内部算法服务承接主线，任务工作器位于业务进程内。这一结构适合现有规模，降低部署与故障定位成本；明确的计算合同和状态接口为后续扩展保留协作边界。

本文将业务事实、模型建议、数学验证和学习证据作为四个不同概念使用。事实来自已保存的原题、作答与事件；建议来自语义计算或支持策略；验证表示某个明确范围内的检查成立；有效学习证据还要求独立性、来源、首次性等业务条件。

### 1.2 系统架构

系统采用客户端、业务控制、智能计算与数据资源四个逻辑层次（图1），实际运行由uni-app前端、仓颉业务进程和Python内部计算服务协作完成。仓颉承接学生意图，整理计算上下文，并决定结果进入学习记录的资格。各运行单元及其访问关系见图2。

系统的直接交互者是学生，以及已有教师、家长和管理员角色。学生发起采集、学习和复习；教师围绕班级任务布置与复核；家长在授权关系下读取报告。参与者通过客户端访问业务服务，不能直接访问模型池、数据库或内部算法接口。外部智能资源提供模型能力，题库及知识资源提供可检索内容，文件系统保存原始图片和导出资源。系统对这些资源分别建立数据、授权和可用性约束。模型返回的文本只是输入给验证与业务决策的候选结果，外部依赖不获得任意业务写入权限。

![图2 容器协作](figures/restructured/04.png)

容器级划分包括uni-app客户端、仓颉业务服务、Python算法服务、MySQL、原始与派生文件、检索服务，以及通过资源池访问的Qwen能力。客户端只面向业务API；算法端接收经过业务层整理的上下文，返回结构化计算结果。仓颉既是调用编排者，也是状态提交者。它负责将计算结果与当前题目、请求版本和执行租约再次核对，再通过事务写入检查点、动作、轨迹和允许的学习更新。持久学习任务的长计算发生在结果提交事务之外，返回后再进入短事务核对与写入。

业务状态保存在服务端，使界面刷新与计算执行分开。前端离开后可重新读取任务，算法失败后可在有效资格下重试，已经受理的动作与历史仍归属于原任务。逻辑模块共享所在进程的运行环境，部署关系按图2中的实际服务和资源组织。

### 1.3 异步确认

模型和检索耗时发生在业务状态持续变化的环境中，因此受理请求与采用结果必须分开。学生提交时合法，只能证明当时允许开展计算；是否允许写回，要在结果返回后依据最新事实重新判断。这一时间语义贯穿诊断、任务、练习和恢复，也是前后端接口协同的基础。

创建任务或提交动作时，业务层先验证身份、题目归属、输入来源和请求参数。受理成功表示动作已保存，不表示模型计算已经完成。客户端读取公开任务状态，根据排队、执行、等待学生或结束等状态呈现相应交互。工作器领取租约后读取上下文与检查点，向Python发起计算。在此期间学生可能编辑题目、取消任务或从另一端提交新动作，因此结果返回后必须再次核对来源与执行资格。只有检查仍成立，才允许事务提交。

第一次确认解决“这是谁的哪个动作”；第二次确认解决“这个结果现在是否仍能影响业务”。两次确认之间不要求学生一直停留页面，也不允许模型自行填补学生回答。这是长任务可恢复与防止过期结果写回的共同基础。

例如，学生开始诊断或反事实计算时，业务层已获取题干、原作答和分析的来源快照。Python执行期间，另一页面修改题干或人工订正诊断。计算结果回来后，仓颉重新读取当前材料，对比输入指纹；不一致便拒绝将旧结论写入新版本，提示重新验证。题目内容变更会清除当前诊断和分析表；已冻结的任务来源快照与相关事件按其接口范围保留，当前题目不会被迟到结果覆盖。关键决策是把“计算成功”和“允许提交”分开，使模型无需持有数据库状态；即便外部模型耗时较长，也只影响等待体验，不改变版本一致性要求。

## 2 模块协同

### 2.1 仓颉业务服务

业务模块围绕题目、用户关系、任务和学习事件组织。仓颉负责身份、资源归属、来源版本、状态转换及MySQL事务，并向客户端提供公开投影。该责任配置使诊断建议、练习判定和教师复核能够共用一致的事实基础，避免不同页面各自维护一套进度。

前端页面按学生任务组织，业务层按事实与权限组织，算法层按计算能力组织。采集、诊断、学习任务、练习复习、知识题库、组卷和角色协作构成主要业务域，各域通过题目ID、来源版本与学习记录关联。业务模块通过共同的题目和事件关联。诊断生成的错因可用于地图导航，但地图读取不会产生新的学习证据；任务中使用知识卡属于支持，不自动等价于独立练习；报告读取既有事实，不重新用模型生成分数。

新增能力沿现有职责分配：判定能力进入算法合同，状态写入规则进入仓颉，操作入口进入前端。跨域变更同步说明输入来源、状态变化及失效规则，使同一题目在不同页面中保持一致含义。

仓颉业务层负责账户、角色关系、题目和学生作答、学习任务生命周期、认知证据与复习安排。它调用MySQL完成持久化，管理媒体与导出的资源访问，并向客户端输出与身份相符的公开视图。任务工作器在业务进程内领取待处理任务，利用租约标识执行资格；完成计算后核对来源并提交事务。身份、版本、重复证据、取消和预算等规则由服务端控制，前端不能通过伪造字段要求直接标记掌握。

仓颉在本项目中的价值是承担了核心业务组织与一致性责任。Python计算可以提供候选判定，数据库操作仍经过业务规则。由此可明确定位：某次错误来自识别、诊断、学习策略还是状态提交，形成从输入到提交的定位路径。

表2  业务职责

| 责任域 | 维护的事实 |
|---|---|
| 身份与协作 | 用户、班级、授权与可见范围 |
| 题目与来源 | 原始材料、修订、步骤和诊断 |
| 任务与恢复 | 动作、检查点、租约与退出原因 |
| 学习记录 | 证据准入、认知更新、复习计划 |

### 2.2 智能计算服务

模型请求统一使用 Qwen 逻辑名称，经 ApiPoolProvider 在配置池内轮询。调用结果先通过 Pydantic 结构校验，再进入具体判定或规划合同。支持的数学关系交给 SymPy 核对；可视化以 VisualizationSpec JSON 返回前端，由既有组件渲染。模型资源选择、结构消费和数学检查分别具有明确入口。

Python/FastAPI提供内部算法入口，承接识别、分析诊断、学习策略、答案判定、可视化、检索及导出等计算。输入经过结构校验，输出以明确合同返回，不能借由模型响应直接修改业务表。部分能力复用backend/app下的提供者、模型和纯计算实现。仓库保留旧Python业务版作为兼容入口，但当前前端没有在仓颉失败时静默切换到旧业务服务。复用代码路径不改变当前业务归属。

前端只调用仓颉业务API，携带用户身份与动作上下文。业务接口表达创建题目、提交学习动作、读取任务、保存自检、开始复习等用户意图，不要求客户端选择数据库表或内部工具执行细节。仓颉到Python的内部请求表达计算所需上下文、当前检查点、动作和预算。返回结果包括学生视图、下一检查点、工具轨迹、判定与退出原因。算法服务的结果不直接视为数据库更新命令，仓颉仍要验证合同、来源和状态转换。

接口设计因此分为公开业务语义与内部计算语义。公开响应屏蔽尚未展示答案、私有评分字段及模型资源信息；内部响应限制结构和允许工具。异常返回也需保持明确含义，避免客户端把未完成计算解释为成功学习。

例如，到期复习开始时，页面先隐藏答案，学生提交作答后生成带来源版本、请求编号和摘要的待评价回执。网络断开重发同一请求，业务层返回原回执；若答案已修改或原题版本改变，则要求重新核对。学生又提交一份新答案时，旧待评价回执标为被替代，不能再用旧结果评价本次复习。这样的两阶段交互把“已经判完但没收到响应”与“尚未评价”分别恢复，避免回到页面便重做一次，也防止两个页面拿不同判题结果安排同一个复习计划。

内部响应必须说明“返回什么”，业务合同则说明“允许造成什么后果”。例如一个格式正确的completed建议不能直接变成学习证据，仍需通过当前租约、来源、动作类型和独立性检查。这样即使后续更换策略实现或增加工具，业务更新资格仍能在仓颉中集中维护。

### 2.3 学习档案

同一道题跨越采集、分析、诊断、辅导、练习和复习，题目档案承担这些事件的共同入口。首页、易错地图与修复路线读取档案，提供与当前记录相符的下一步；组卷、报告和角色协作复用已有事实。由此既保留功能完整性，也避免浏览页面本身制造新的学习成绩。

一道题目关联原始图片、识别校对、题干选项、学生答案与步骤。后续分析、诊断、教学会话、任务、练习、复习和试卷都通过明确关联进入该上下文，保证不同页面谈论的是同一学习对象。题干和作答修改不是纯界面操作。它们改变后续结论的输入，必须推进修订并使依赖旧输入的分析或任务失效。题目内容变更会清除当前诊断、诊断证据、分析和参考步骤，并撤销相关当前资格；归档与已冻结任务快照分别处理。新结果基于现行材料重建。

详情页将题目、学习和记录分区，服务端提供必要投影，避免客户端自行拼接无权限或已过期的内容。题目作为主线使学习过程可回查，也使恢复、报告和人工复核拥有共同的事实入口。学习档案汇总题目的教学、订正、任务、练习与复习记录，并保留各自结果含义。修复路线从档案决定建议下一步，不因用户浏览某页就改变完成状态。易错地图按当前有效诊断归组，提供原题和依据入口。

投影读取应遵守范围和版本规则。地图聚合结果保留题目来源、日期和截断范围。归档或来源变化的数据不能继续作为确定的当前弱点，仅已保留的任务快照及事件可按实际入口回查。只读页面本身不写学习证据。这使首页推荐、地图浏览和报告查看不会抬高掌握估计。学生进入这些页面所获得的是行动导航，真正的状态更新仍由作答、验证和复习事件支持。

题库练习从当前学习目标生成查询，候选通过相关性和内容资格检查后展示。学生作答关联原题指纹和候选版本；同题同模式已经完成后再次提交返回 HTTP 409，内容变化后也拒绝旧资格。任务与复习则按各自合同恢复回执，不能把该行为套给题库练习。题目推荐的相关性因此进入业务合同，而不只依赖检索模型排序。

组卷以所选题目、顺序、分值与标题形成保存对象，之后生成题目PDF、答案PDF和表格。导出资源保持归属和访问保护，页面操作失败时保留当前编辑并允许核对保存状态。文件结果必须与已保存内容相符。教师布置和学生提交沿用题目及作答基础，人工复核产生明确反馈。家长报告以学生授权和实际关系约束，管理员查看既有受控信息。各模块拥有自己的动作与权限，却不另造一套与学生学习事实冲突的数据。

例如，学生获得一道真实题库练习后离开页面，期间题库答案或原错题知识目标发生更新。提交时业务层锁定学生原题和题库题，确认该题具有自动判分资格、确实曾向当前学生提供，并核对目标、内容指纹与适配证明。旧证明失效就重新做内容适配；不匹配返回冲突，且不写入练习成绩或掌握变化。判题仍需核对时，返回不确定反馈和参考解析，不把它固化为确定学习证据。已完成的同题同模式练习再次提交也被拒绝，防止重复积累证据。

## 3 业务机制

### 3.1 材料采集

以下以一道单位换算题贯穿材料、诊断和任务设计：汽车以72 km/h匀速行驶10 s，求路程。学生记录“s=vt”，继而写出“72×10=720 m”。正确换算为72 km/h=20 m/s，路程为200 m。该例用于说明数据与操作关系，各环节依据学生实际输入推进。

输入链路首先建立可信学习对象。照片、OCR候选、学生确认后的题干、学生当时作答和派生清洁图具有不同语义；它们以来源关系连接，不能互相覆盖。系统将保存原件、识别候选与确认输入设置为不同确认点，后续诊断才能区分识别偏差与真实解题偏差。

采集开始于原始图片或手工题目。图片处理产生裁剪、清洁等派生材料，识别与结构化计算输出题干、选项和可确认字段。用户核对后建立当前学习对象，后续分析以该确认版本为来源。采集链中包含多个不同确认点：上传成功只说明材料已保存，识别成功只说明获得候选文本，学生确认才表明当前题干可作为后续输入。若识别任务中断，保存的材料支持恢复，保持同一来源关联。

原图与派生资源分别管理。人工修改和重新识别改变当前输入，并触发分析、诊断与资格失效；已冻结任务快照与相关事件按实际入口保留。这样可以区分“识别错了”和“学生算错了”，并为之后的诊断提供可靠起点。题干图片、学生书写、最终答案和步骤分别保存。图片保留视觉原件；题干和选项形成可计算描述；答案表达本次结果；步骤提供诊断依据。只有答案时，诊断保留答案层面的证据范围。

手写任务先保存照片，再执行转写，学生可以编辑并确认识别结果。模型观察到的图形标记属于候选证据，必须结合原题核对。辅助使用也需要进入后续独立证据判定。前端把确认动作放在计算输入之前，让学生有机会纠正识别问题。服务端记录来源和版本，在同图重试、任务恢复和并发提交中维持一致关联，避免既有照片、识别草稿和新答案发生错配。

表3  输入材料

| 材料 | 语义 | 需要的核对 |
|---|---|---|
| 原始照片 | 视觉来源 | 格式、归属与保留 |
| 识别文本 | 模型候选 | 学生修改确认 |
| 学生步骤 | 当时推理记录 | 稳定步骤ID与版本 |
| 最终答案 | 本次结果 | 题型及判定范围 |

上传端检查格式、大小和像素约束，媒体读取检查签名、路径和归属。无效输入在进入耗时计算前拒绝，处理失败返回明确错误状态。派生文件不能替代原图成为唯一证据。重复识别和异步重处理需要核对现有任务、题目归档状态和修订关系。学生编辑题干后，旧识别或分析回执不能重新激活过时内容；异常中断后读取已经保存的状态决定继续、重试或结束。

对前端而言，采集错误应在相应操作附近持续显示，并保留输入及可恢复入口。服务端返回明确状态，客户端不通过本地假数据补齐。采集的稳定性与后续智能质量相互关联，因此原图保护、校对和恢复都属于核心业务设计。

### 3.2 错因回放

单位换算案例中，第一步公式成立，第二步直接将以小时为单位的速度与秒相乘，产生单位不一致。回放同时展示学生第二步原文、题目中的单位条件和换算建议，使学生能够定位需要修改的环节。该物理示例采用语义核对及人工确认路径，形式化验证标签仍按实际工具结果赋予。

诊断围绕学生实际路径展开，不要求学生按参考解析的同一顺序作答。结论同时携带定位、引用与验证范围；结构合法、数学关系成立和学生形成有效学习证据分别检查。回放与人工修正把诊断重新连接到学生的原过程，使结论保持来源可查。

诊断输入包含题目条件、参考资源、学生答案与步骤、题型和必要图片。参考与学生路径可能不同序、不同长，正确性应在题目条件下判断，不能以同一数组位置作为必然对应关系。支持规则验证的方程或不等式优先使用原题关系核对。其他题型使用模型语义诊断时，首错必须落在实际学生步骤范围内，并原样引用该步；无有效定位时保留为空。系统不会为了让页面完整而补造学生过程或参考步骤ID。

诊断输出同时包含错因类别和证据范围。类别归一到系统支持的学科分类，未知代码降级为未知。定位、类别和修复建议在后续回放、人工修正与任务支持中复用，因此其来源比一句看似完整的解释更重要。

例如，原题和参考解答已保存，但学生采用了更短的正确路径，学生两步不能与参考四步逐行相等。提交诊断后，计算层先识别支持的规则范围；不能套用形式化规则时，以学生真实步骤进行语义审查，引用实际下标和原文，不再把同序参考行强塞成对应关系。若答案与过程为正确或等价，首错清空；有疑似错误则保留建议等级。模型给出越界下标或无法解释的位置时，不构造不存在的步骤。这样保留多路径解题空间，同时让回放页面知道哪些定位需要学生核对。

Pydantic检查字段类型和结构合同，解决结果是否可安全消费的问题。数学规则核对表达式、解集或条件，解决限定范围内结论是否成立的问题。教学证据门槛还要检查是否来自学生独立作答、是否使用辅助、来源是否仍然有效。三者不能互相替代。

未通过本地规则证明的修复建议以待核对状态保存和展示。与参考文本一致仅表示一致性，不等于已证明原题结论；模型给出的反事实修复也不能自动宣称根因确认或恢复了多少后续步骤。前端使用清楚的中文标题和提示呈现范围，具体公式在数学组件中显示。历史或人工修改导致证明失效时，旧建议不继续显示为确定正确。

例如，某个受支持方程已定位首个错误，学生前面几步其实正确。系统尝试只修复该处并检验后续能否恢复，而不是重新生成一条完全不同的标准解。核验关注首错是否被修正、前缀是否保留、后续有效步骤是否恢复；因此“生成过程看起来正确”不足以确认根因。对于规则尚不支持的题型，模型修正只是一份待核对建议。历史缓存若只做参考文本对齐却自称符号证明，会在读取时降为旧建议；人工调整首错后，旧反事实证据同样被标为需重新核对，而不删除原记录。

回放按原始步骤呈现当时作答和可用诊断依据，让学生知道结论指向哪一处。若证据不足，可补充过程、重新核对或人工修正。人工改变错误位置后，原有修复证明与参考对应必须重新判断，不能把旧建议直接当作新位置的正确做法。

易错地图把当前有效诊断按学科和错因归组，每项保留原题入口。单题是一次线索，多题重复是值得关注的现象，并不自动等同于固定认知缺陷。未定位、已归档和来源失效的内容应按实际范围处理。从诊断到地图再到任务，数据关联持续保留。地图选择一个节点后进入原题和修复路线，路线读取档案决定当前动作。该结构支持个人化导航，却不会因学生浏览某组内容就自动生成一份新的学习成绩。

例如，学生只填写最终答案时，系统围绕答案和题目条件给出分析，首错位置保持为空。页面保留该次原作答，并提供补充步骤和核对类别的入口。学生补齐实际过程后，诊断才能关联具体步骤；语义建议保留待核对状态，支持规则的结果附相应验证依据。这样，数据完整程度直接决定诊断粒度。

### 3.3 任务智能体

沿用单位换算案例，任务先围绕速度单位转换组织支持，再要求学生独立求出路程。系统保存每次回答、是否查看提示和当前检查点。学生答出20 m/s仅完成局部订正；进一步给出200 m才提供整题作答。条件对照由题型能力决定，任务状态与学习证据分别写入。

当前智能体由持久任务协调器和受约束的计算循环组成（图3）。仓颉保存目标、动作与检查点，负责跨动作推进；Python根据本次观察选择支持方案，调用允许工具，并据反馈调整当前执行。工具结果提供后续选择的依据，最终状态仍经业务校验提交。

![图3 任务智能体](figures/restructured/06.png)

持久任务围绕question_learning目标组织，保存当前学习阶段、尝试、辅助标记和必要检查点。观察来自原题来源、学生动作、有效记忆和工具反馈；规划提出下一项支持；执行生成可验证结果；业务提交决定其是否进入当前状态。任务状态独立保存。学生离开后仍有可读取的状态，动作有独立请求标识，工具步骤与计划版本可以审计。一个动作中的自动调整受次数和时间预算限制，等待学生时真正结束当前执行，不由模型代答继续。

例如，已完成分析的原题被学生连续点击“开始”，或移动网络在响应前断开后再次发送同一创建请求。仓颉以用户和请求编号查找已有记录，并核对提交内容摘要；相同请求恢复既有任务，不新增一组独立学习历史。另有同题活动任务时，业务层复用或明确处理现有状态，避免两个页面同时训练同一道题而重复计分。若请求编号相同但内容改变，则拒绝混用。此设计把网络重试视为传输行为，把真正的新一次学习视为业务行为，不依赖按钮禁用来保证数据正确。

策略输入采用经过业务层筛选的上下文和有效记忆，模型可以提出支持目标、工具和公开决策摘要。系统校验工具白名单、字段和记忆引用，非法或无法使用的计划转入受控规则支持，不执行模型随意命名的工具。工具结果是后续选择的观察。知识检索零命中时，系统可以转为步骤核对；学生答错时，保留当前阶段并补充支持；有效订正后进入独立作答。反馈因此影响下一行动，并保存调整依据。

有界重规划避免无限循环和无上限资源消费。单次执行工具轨迹有上限，任务还受累计回合、执行和共享时间预算约束。耗尽后保留历史并明确停止或重开。规则回退和模型来源分别记录，不能把回退生成的支持写成一次成功模型推理。

例如，学生在独立作答阶段出错，智能体观察本次反馈后选择知识检索、步骤对齐或图示支持。策略只允许有限工具和结构化输出；知识检索无命中、图示不适用或工具证据不足时，系统在预算内调整为另一种实际支持方式，而非直接宣告学生理解。工具轨迹记录验证等级和调整原因，学生只看到当前一步和可操作反馈。模型提出未允许工具或格式无效时，合同校验与受控回退阻止自由执行。帮助是否使用也单独留下标记，为之后独立性门槛提供依据。

|---|---|
| 知识未命中 | 换用步骤核对或请求补充 |

工具轨迹记录支持目标、计划来源、工具名称、验证状态、证据范围、耗时与记忆引用。它描述系统做过什么以及结果为何可用，不保存或展示模型隐藏思维链。学生历史主要呈现动作、反馈、对应步骤和辅助标记。输出StudentView包含标题、受控内容块、输入方式与允许动作。前端据此呈现一步交互，不渲染任意模型脚本。图片、图示与历史查看均遵守归属和来源规则，内部答案与评分字段不因调试需要直接暴露给学生。

审计的价值在于复现关键业务判断。非法工具、重复提交、在途来源变化或最终事务失败，应能从动作与轨迹解释原因，并确认没有产生部分学习更新。真实持久记录比一张工具调用截图更能支撑智能体机制的说明。

当前任务工具包括步骤核对、答案判定、知识检索、步骤关联、条件对照、手写识别、图形观察和受控图示。工具只能按已实现合同执行，不能把模型给出的函数名解释为任意代码权限。工具轨迹的验证结果区分verified、rejected、needs_review与not_applicable；这些标签说明该次工具检查，不自动描述整道题或学生整体能力。单次结果至多保存三条工具轨迹，计划与实际调用均有范围限制。

### 3.4 独立训练

独立训练沿局部订正、原题作答和条件对照逐步推进。局部订正检查关键步骤，原题作答检查完整求解，适用题型的条件对照进一步观察学生对单项条件变化的应对。任务保存各阶段的回答与辅助记录，给出提示或展示答案后，将该阶段标记为 assisted。

在单位换算案例中，学生先把72 km/h换算为20 m/s，再独立求出10 s内的路程。前一结果说明单位转换已订正，后一结果说明本题求解完成。系统根据题型能力安排后续条件对照；仅完成原题时，保留过程与自检结果。不同阶段产生的观察分别进入相应合同。

题库推荐从当前目标、题干和知识点构造查询。Python通过BGE稠密与稀疏召回形成候选，融合后重排；Qdrant提供索引访问。仓颉按候选ID回查MySQL，核对学科、年级、答案、可用状态及目标适配，保存推荐来源和版本。提交作答时再次核对资格，保证页面所示内容与判题依据一致。检索排名用于缩小候选范围，内容适配决定能否用于训练。

例如，单位换算错误触发的推荐应检查速度与时间单位的关系。一道仅在文字上同样出现“汽车”的统计题，可能获得较高相似度，却缺少当前学习目标；适配检查会排除它。有效候选具备明确答案和判定条件，学生完成后能够得到与本次练习相对应的反馈。题库题在展示后若被修改，原推荐资格失效，页面需重新取得现行内容。

掌握估计由有效学习证据经规则计算形成，用于组织后续支持与复习。业务服务先核对事件资格，再与动作结果一同提交认知更新。持久学习任务的近迁移更新要求真实 answer 动作、有效 contrast 作答、confirmed_correct、未受辅助、判题允许更新、可验证对照及事件尚未应用。对照曝光按学生和题目内容去重，使同一内容跨错题重复出现时仍能识别既有曝光。

### 3.5 复习调度

复习记录学生在一段时间后的再次作答，保存判题、本人反馈和下一次安排，并可作为后续任务的有效记忆。图4给出三类学习事件的写入关系：复习维护回忆记录与计划，持久任务和独立题库练习分别按各自资格形成认知规则证据。复习的当前写入链与掌握更新入口分开维护。

![图4 学习事件分流](figures/restructured/15.png)

复习安排关联原题与有效来源版本。学生先回忆并提交，再核对结果及反馈；系统结合实际判题和难度自评决定规则式间隔，不把“感觉容易”当作错误答案已经正确。系统采用按判题结果和反馈调整间隔的规则式调度。复习结果与下次计划通过原题和回执关联，掌握估计则由独立的学习证据写入链维护。请求回执丢失后可读取已有结果；重复提交不生成多个下次计划；来源改变后旧回执失去当前评价资格。学生可回原题核对并进入新的学习流程。

时间间隔使同一题目产生新的观察。学生再次答错时，后续支持可以返回当前偏差；独立回答得到确认后，复习节奏依据对应规则调整。记录保留作答时点与来源，便于解释两次表现之间的变化。

例如，学生完成复习作答后选择“很轻松”，系统先确认回执仍是当前、来源未变且判题达到可用于复习调度的确认条件，再结合实际正确性安排下一次。答对且轻松可延长间隔，答错即便自评轻松也只获得较短间隔；判定待核对时暂不更新计划。当前待复习计划与回执状态在事务中同步完成，再创建新计划，避免已经完成却没有后续安排。这里采用可解释的规则式调度，自评影响节奏但不充当正确性证据。

## 4 数据管理

### 4.1 数据组织

数据模型以题目、来源、动作和结果建立关联（图5）。MySQL保存用户归属与业务事实，受控文件存储保留原件及派生产物，Qdrant提供可重建检索索引，客户端缓存保护尚未提交的输入。学习事件通过题目与版本连接，使每个结果能够回查到当时的材料和学生行为。

![图5 数据关联](figures/restructured/10.png)

概念模型围绕学习对象、来源、动作和结果建立关系。用户拥有题目，题目关联原始资源与当时作答，诊断关联版本和步骤，任务关联来源快照、动作、检查点与工具轨迹。练习和复习结果再进入各自的学习证据及后续安排。模型强调稳定关联而非复制内容。原始材料长期可回查，派生结果说明计算所依据的版本；题库和索引属于可独立维护的资源，候选内容还要经过业务层回查。不同记录具有不同状态和权限，不以一个通用JSON对象取代所有业务关系。

核心关系中最值得保留的是事件归属与来源。动作属于一次任务，任务冻结某版题目，判定说明对该动作的范围，复习计划关联有效原题。没有这些关联，单独保存一个“正确”字符串无法支持后续恢复与解释。

业务事实包括题目、用户作答、任务动作、有效学习结果和授权关系，由MySQL维护。诊断和摘要属于基于来源生成的派生结果，需要保留其输入指纹、版本和证据范围。原始文件保持独立，清洁、裁剪和导出资源具有各自用途。Qdrant保存用于召回的索引信息，其命中必须回查业务内容。索引过旧、候选删除或题目改写时，原分数不能保障当前可用性。前端缓存主要用于登录状态、草稿与提交恢复，不承担跨设备一致性事实。

这一分工使数据变化的影响可预测：修改原题会影响诊断与任务来源，题库内容变化会影响推荐资格，撤回授权会影响报告读取。通过来源关系处理失效，比在各页分别清空局部数据更可靠。

表7  数据分工

| 数据类别 | 权威位置 | 失效/更新方式 |
|---|---|---|
| 业务事实 | MySQL | 经权限和事务规则修改 |
| 原始文件 | 受控文件存储 | 保留原件并管理访问 |

| 本机草稿 | 客户端缓存 | 按用户/题目/任务隔离 |

### 4.2 来源版本

当前诊断与分析采用失效后重建；持久任务则冻结来源快照，保留对应任务事件。两类数据并不具有同样的历史保存策略。当前状态按现行材料判断，已冻结任务的历史按其当时快照读取。题目编辑、作答修改、诊断修正和资料撤回都可能影响派生结果，因此来源检查必须贯穿创建、执行与提交。历史可读不代表旧结果仍具有当前写入资格。

来源指纹把当前计算与题目及作答版本联系起来。开始学习时保存快照，学生回答与工具结果都关联这一来源；回读历史时使用对应快照解释当时内容，而不是把当前题干混入旧记录。计算和业务修改可能并发。系统在受理、领取、结果提交等关键阶段核对来源；在途更新不应提交旧证据。即使任务本身尚未超时，输入改变也会使其失去当前提交资格，这一判断与网络请求是否成功相互独立。

来源一致性也适用于记忆和题库推荐。旧摘要不能绕过原记录失效，旧推荐不能在题目改变后继续判分。题目编辑会实际删除当前诊断、诊断证据、分析和参考步骤，取消待复习计划并给已有练习、复习等记录标记来源变化；任务快照的保留不能推导为旧诊断表完整归档。

例如，某次学习开始时，系统保存原题、分析、诊断与学生步骤的快照，并记录真实步骤ID及输入指纹。之后学生改了答案或题目，旧任务的历史仍应展示当时的材料，而不是拿今天的题目解释昨天的错误。读取或执行时，仓颉将快照与当前来源核对，不一致则把任务视为失效；历史仍可回看，新学习要从现行原题创建。对于没有快照的旧任务，仅在现行来源验证一致时补录，不能为已经过期的记录编造“当时”的材料。数据版本由此成为教学证据的一部分。

来源指纹连接题目、分析、诊断、作答与真实步骤身份。来源快照不是把客户端传来的ID照单全收，而是业务层读取当前归属后生成。结构化数据比较保留对象字段、数组顺序、布尔与字符串的差异；JSON数值1与1.0等传输表示差别则按实现允许等价，避免数据库表示变化误触发失效。该规则关注业务输入意义，而非简单比较某段格式化文本。

### 4.3 任务状态

运行状态与教学阶段是两套正交概念。前者说明是否正在执行、等待或结束，后者说明本题正在订正、独立作答还是进行条件对照。请求标识、版本与步骤资格把状态转换绑定到真实学生动作，使弱网重试、重复点击和多页面并发不再依赖界面按钮维持正确性。

![图6 任务状态](figures/restructured/08.png)

运行状态包括排队、执行、等待学生、待核对、完成、失败、取消和来源失效，转换关系见图6。教学阶段则包含局部订正、原题独立作答、条件对照和结束。同一教学阶段可以经历多次等待或恢复，公开任务状态与阶段信息共同决定页面当前动作。

任务结束时保存本次过程，学习更新另外检查证据资格。后续题目变化会改变历史任务对当前材料的有效性，系统保留完成记录，并在读取时标识来源变化。这样既能追溯过去的学习，也能从现行版本重新开始。

客户端消费公开状态与StudentView展示当前一步，内部评分依据和未展示答案由服务端控制。终态保留记录，不再自动执行；允许的重开创建新的当前学习流程，并与历史来源区分。例如任务在独立作答阶段调用判题后暂时失败，其教学意图仍是独立作答，业务状态却是failed。恢复应继续该阶段，而不是把它当作新的一题重新给出全部提示。相反，已经完成的历史任务在题目变更后可标为来源失效，历史事实仍保留。

长学习计算采用先受理、后读取结果的方式。客户端收到受理回执后，以任务状态判断是否等待或展示下一步，不能依据一次HTTP返回就自行改变完成状态。轮询与页面恢复都读取同一服务端事实。幂等请求将重试与新动作区分。网络断开、回执丢失或刷新后，界面保存待确认请求标识，并先核对服务器是否已应用；同一请求重放不产生重复学习证据。新的回答则需要当前版本与步骤资格。

错误语义区分参数非法、权限不足、来源冲突、资源暂不可用和任务待核对。学生能看到可采取的操作，例如核对状态、回原题、继续或结束；服务端不会为避免报错而假装已有可靠AI结果。

例如，学生已在任务当前步骤作答，但返回包丢失。前端携请求编号、版本、步骤ID和来源指纹重新提交，仓颉比较已存动作的摘要；内容相同就返回现有任务状态，不再执行一次判题或重复应用证据。若学生修改了答案却沿用原编号，系统明确返回冲突；若页面版本已落后，保留输入并要求刷新。只有属于允许交互状态的新动作才进入排队。幂等检查与版本检查共同区分“同一次操作重试”和“新的学习意图”，让刷新、弱网和多页面操作有可解释结果。

### 4.4 学习记忆

个性化建立在可追溯的学习记录之上。任务开始及提交核对时，系统从有效业务来源重建受控记忆。事实、规则估计、学生自述和复习提醒各自保留类型，使不同强度的依据可以参与策略选择而不混为能力证明。

学习记忆由真实来源构成，类型区分事实、估计与学生自述。读取时核对用户、学科、来源版本和有效期；已删除、撤回或过期来源不能作为当前计划依据。模型接收当前任务所需的受控快照。

保存一次自检要点代表学生确认了一条提醒，可以影响后续支持，但不自动提高掌握估计。复习“感觉容易”的反馈也不能覆盖实际错误。记忆摘要必须带可回查引用，防止浓缩后的文字脱离原记录成为无法纠正的结论。

计算在途期间如果来源失效，提交时应拒绝使用旧记忆结果并保持事务一致。记忆不仅提高个性化，也需要撤销机制：学生修改、删除与解除授权后，后续策略应停止引用失效内容。

例如，学生已有掌握估计、练习结果、自检要点和复习安排，新任务希望利用这些信息选择帮助方式。仓颉每次从业务来源重建记忆，并附用户、学科、类型、版本和有效期；掌握估计仍是估计，自述仍是自述，安排复习不代表学会。某条教师复核被撤销、原题被修改或题库题内容变化，相关记忆不能继续以旧版本参与规划。提交前还会重新构建上下文，若执行中依据已变则拒绝落地。有效记忆既使个性化跨任务延续，也让后续纠错能真正撤销其影响。

当前记忆实现对掌握估计和误区候选使用30天范围，对有效学习事件、自检和复习来源使用90天范围，并设置各类条目数量及摘要长度上限。此时间范围用于上下文筛选。误区状态以候选使用，学生自检以自述使用，复习计划以提醒使用；即使文本内容相似，其证据强度也不能合并。

每次执行保存所采用引用、版本、分类、观察时间和失效时间构成的清单。结果提交前重建上下文并比较，能够发现计算期间发生的题目修改、复核撤销或自检删除。若清单已不再有效，旧结果失去落地依据；来源撤销因此会真实影响下一次规划和在途提交，而不只是从页面隐藏一条历史。

## 5 安全部署

### 5.1 角色权限

访问控制同时核对角色能力与对象关系（图7）。教师在所属班级和作业范围内开展复核，家长依据学生授权读取报告，学生管理本人学习材料。仓颉为每次读写检查实际关联与当前权限，前端据此提供相应入口。

![图7 角色权限](figures/restructured/11.png)

权限由角色与资源关系共同决定。学生访问本人题目、任务和记录；教师访问其班级和布置任务范围；家长通过学生明确授权读取相关报告；管理员使用专用身份访问受控管理接口。每次资源读取与写入都需检查归属或关系。

登录与注册不能由用户输入提升为高权限角色。前端隐藏入口只帮助交互理解，实际访问拒绝由业务端执行。媒体、试卷和内部关联资源也需遵循同样范围，避免通过已知ID或文件地址绕过题目权限。

权限图区分业务服务的信任边界与外部参与者。内部算法只获得当前任务所需材料，不继承任意用户查询能力；模型响应也不能提出一个越权工具并获得执行。授权、事实和计算在边界上分别校验。

例如，教师对自己班级的学生作业进行人工复核，业务层从已认证教师推导班级和学生范围，不能采信请求体中的任意teacher_id。复核可在满足条件时形成学习证据，同时记录前后状态及审计。后来撤销或纠正复核时，系统检查是否已有更新的提交或其他学习结果，避免把较新的学生进展无差别回滚；撤销影响相关有效记忆，保留原始作答和审计。越权班级、错误角色或审计写入失败均不应留下部分复核结果，使教师确认成为可追溯业务动作，而非直接修改一张总分表。

家长关联由学生明确确认后建立，系统检查双方关系并限制报告范围。学生或家长解除后，服务端后续读取立即按新关系判断；旧页面刷新不能继续获取已撤回的数据。教师复核围绕班级和任务关系展开。学生提交自动计算结果后，教师可对相关内容进行人工核对并形成反馈；班级成员变化、任务归属与既有复核责任应按业务规则处理。人工复核保留其身份和事件来源。

这些机制让协作能力与学生主线保持一致。报告读取不生成学习成绩，人工确认也不回写原始照片或覆盖学生当时答案。后续若对接学校身份系统，需要单独设计与验证，不作为当前已经具备的能力描述。

例如，家长账号存在但尚未与学生关联时，不应仅凭知道学生姓名或ID读取报告。学生在自己的账户明确确认授权，业务层锁定学生记录、核对目标账号为guardian，并去重和限制关联数量，随后建立报告查看关系。学生或家长都可解除关系，重复解除安全返回；后续报告访问按现存关联重新校验。授权不把题目所有权转给家长，也不赋予其教师复核能力。撤回后，服务端按更新后的关系拒绝后续报告读取。

### 5.2 资源安全

安全边界覆盖原始材料、派生文件、模型凭据和前端生成内容。系统保留原图，受控交付图片和导出物，算法只接受约定结构，前端只渲染受支持的内容规格。模型服务与文档分发使用不同资源边界：正式材料说明依赖，但不能携带可直接调用的私密配置。

原图和导出文件使用受控访问地址，服务端核对签名、有效期及路径边界，防止通过用户输入访问任意文件。资源刷新时重新获取当前有效地址，避免长期缓存过期签名导致下载或图片读取失败。实际模型池、访问令牌和环境配置留在本机受控配置中，不写进手机端、参赛文档或公开源码包。部署者按安全示例配置自己的资源，文档说明依赖与使用方式，不复制私有地址或密码。日志和错误报告避免打印池内凭据。

数学与图示内容采用受控结构显示。模型不能通过返回JavaScript扩展客户端权限，未知内容块也不作为可执行脚本渲染。安全边界服务于功能正确：学生的材料不被误覆盖，别人的数据不混入当前学习，异常输入不触发未授权操作。

例如，学生将自己的错题编成试卷并选择题目PDF、答案PDF或Excel。仓颉先核对试卷归属，按顺序聚合原题、分值、选项、分析和所需配图，再把快照交给Python排版计算。返回文件必须满足非空、大小及SHA-256一致性，随后保存派生文件和导出记录，并提供签名访问或归属校验后的下载入口。渲染失败不产生完成记录，记录写入失败会清理刚写出的文件。下载不存在的产物提示先生成，下载请求限定在获授权的产物范围内。

表10  资源保护

| 对象 | 保护方式 |
|---|---|
| 媒体/导出 | 签名、时效、路径与归属 |
| 模型配置 | 私有保留，示例不含可调用凭据 |
| 生成内容 | 结构化校验、受控渲染 |
| 报告与审计 | 公开投影与敏感字段过滤 |

### 5.3 运行部署

当前部署采用适合个人学习与项目验证的本地服务组合（图8）。前端、业务服务和内部算法分别启动，数据库、文件及检索资源提供支撑。接手者按照依赖和调用方向检查环境，再运行实际学习流程确认业务可用。

![图8 运行部署](figures/restructured/12.png)

当前运行由前端开发或构建资源服务、仓颉业务进程、Python内部算法进程、MySQL及按需检索资源组成。仓颉进程内包含识别与学习任务等工作器，不依赖单独消息队列。部署配置决定实际端口和媒体位置，文档不把本机回环地址当作公开体验域名。

客户端通过业务服务处理身份和所有学习请求，内部算法使用服务端密钥约束访问。检索需要对应模型与索引资源，外部Qwen需要有效资源池配置；数据库与文件系统保存业务和材料。它们应分别检查就绪状态与实际功能。手机通过可达的HTTPS业务入口连接同一服务拓扑，网络入口按部署环境配置。

接手环境先准备仓颉工具链、Python和前端依赖，再配置独立MySQL及业务环境。当前主线入口是make install-final、make dev-final和make check-final；初始化数据库与准备题库是明确动作，启动器不会静默创建演示成绩。

健康检查分别确认业务服务、MySQL表版本、算法服务和前端是否就绪。它不调用付费模型，因此不能代替模型质量核验；检索接口成功也不能证明候选相关性。评审准备应再运行一条明确的实际智能流程，并确认图像、题库与导出资源可访问。

评审场景中需要交代本地运行依赖与特殊资源，提前准备公开自编样本和可解释的随机输入路径。模型资源暂不可用时，按官方要求说明事实并提供可核验证据；配置错误或额度不足则属于交付准备问题，不能用静态界面替代运行。

### 5.4 任务恢复

持久任务从MySQL中读取动作、检查点和执行资格恢复学习。正常执行依次完成请求受理、工作器领取、内部计算、结果提交和客户端回读（图9）；每一步具有独立的确认点。取消、来源变化和预算耗尽都会改变结果的提交资格，处理规则围绕这一资格展开。

![图9 任务时序](figures/restructured/07.png)

工作器在事务中领取任务并生成租约，将领取资格绑定到当前执行。计算在提交事务之外进行；结果返回后，业务层重新锁定任务，核对租约令牌、来源版本、取消标记及剩余预算，再共同写入检查点、动作结果、工具轨迹和允许的学习更新。末尾核对或任一写入失败时，整个提交回滚。

执行租约为90秒，单次业务计算与提交共享45秒预算，内部算法计算最多使用38秒，为来源核对和写入留出时间。累计任务另外受24轮和72次执行限制。预算在领取、计算和提交阶段连续检查，耗尽后登记合法的失败状态及恢复入口。

例如，单位换算题的判断已经由Python返回，提交时却发现学生刚刚修改了原题时间。仓颉按新来源拒绝旧结果，相关学习更新随事务回滚。学生回到现行题目重新学习；旧动作及其来源继续用于解释这次执行经过。

重启恢复从持久检查点继续。进程中断后，新的合法执行可在租约过期后领取任务；迟到执行持有的旧令牌无法通过提交核对。两个执行器同时观察到排队任务时，事务锁与领取条件决定唯一有效执行，原始照片及步骤继续关联同一任务来源。

学生主动结束时，仓颉将任务置为 cancelled、递增版本、清除租约，并取消尚未处理的动作。界面收到结束状态后保留历史，在途计算稍后返回也失去提交资格。关闭页面则只改变客户端活动状态，任务仍按服务端事实执行；两种操作对应不同业务意图。

表12  异常恢复

| 异常事件 | 提交资格 | 恢复行为 |
|---|---|---|
| 学生取消 | 旧计算失去资格 | 保留历史并停止任务 |
| 单次预算耗尽 | 拒绝迟到提交 | 登记失败及恢复入口 |
| 来源变化 | 旧依据失效 | 从现行题目重新开展学习 |
| 进程重启 | 按持久状态重新领取 | 恢复原检查点与材料关联 |

客户端按用户、题目、任务及步骤保存草稿和待确认请求。回执丢失时先回读任务状态：已应用的动作展示现有结果，尚待确认的动作使用原请求标识恢复。来源更新后，旧草稿作为待核对内容保留。输入保护与服务端幂等共同减少重复操作，并让学生离开后仍能接续当前学习。

复习和独立题库练习采用各自的事务及恢复合同，分别遵循复习回执和已完成练习冲突规则。界面根据接口语义提供继续、核对或重开的操作，维持跨页面一致的学习状态。

### 6.2 模型核对

真实模型核对补充工程夹具无法回答的内容问题：给定学生路径，答案含义、步骤定位和反馈是否合理。以下记录与受控协议测试分别解释。真实Qwen核对使用12道自编固定样本，包含正确不同路径、负系数不等式、增根、定义域遗漏、条件不足、单位换算、守恒及语言和生物正确作答。核对标准是答案、定位和说明的实际含义，而不是与预期解释逐字相等。

补测发现参考行号覆盖导致正确路径误判，修复后按实际学生步骤定位，并清除超界或不适用下标。分类同义归一与未验证建议提示也纳入回归。物理、化学和概率三题进一步完成真实持久任务，确认原错误与步骤保留。

### 6.3 验收复现

可复现材料应让评审从一个设计结论追踪到代码责任、状态后果与对应验证。正常闭环说明主要功能协同，来源变化、重复请求或取消等异常分支说明结果不会越权写入。代码定位和测试日期统一收录在配套《技术事实核验表》中。

复现从源码版本、依赖配置和数据准备开始。运行指南说明主线入口和外部资源要求，验收记录说明本轮日志与范围。测试环境采用隔离库，实际模型脚本会创建独立QA数据并消耗模型请求，应与日常学生数据区分。演示可从一题录入或已明确来源的自编题开始，展示校对、诊断、回放、任务订正与独立结果，再到复习或导出。异常演示可选择来源修改、重复请求或模型不可用，说明系统如何保留记录和拒绝无效写入。随机输入则按支持范围现场判断，不保证任意证明题都能自动处理。

正式参赛还需准备运行材料、演示视频与团队披露。当前文档提供架构和证据定位，团队据真实情况核对报名信息、评审访问地址、成员贡献和已有成果，并说明源码快照与开发历史的对应关系。

## 7 移动应用

### 7.1 移动交互

手机 App 以“今日、错题、学习、我的”为主要导航，把拍照收录、错因回放、专项练习与复习安排组织为短步骤操作。首页突出当前最值得完成的一项学习任务，历史图表和解释按需展开；新账号以录入入口和学习偏好建立起点，积累真实作答后再形成个人薄弱线索。

采集界面衔接相机、相册和手工补充。照片预览之后进入题干及作答校对，长题干分区阅读，原图始终可回看。以单位换算题为例，学生确认“72 km/h”和“10 s”后，再补充两行计算过程；识别结果与原图保持对应，避免一个单位误读影响整条后续学习链。

错因回放页面围绕当前偏差步骤展开，原作答、依据和订正操作在相邻区域呈现。专项学习一次只显示当前问题、输入区与必要操作，帮助和历史作为次级入口。提交后由服务端状态控制下一步，切换页面再返回时恢复同一任务与来源。

uni-app/Vue 3 负责跨端界面、输入和平台调用，仓颉业务服务提供统一 API，Python 保留在服务端完成计算。应用通过可访问的 HTTPS 业务地址读取数据；模型池与数据库凭据由服务端管理。相册路径、图片旋转、WebView 公式、Canvas 触控、DPR 和文件打开属于平台适配对象。

移动网络下，客户端先保存草稿与待确认请求，再提交服务器。退后台或重新进入时回读任务状态，判断上次动作是否已经生效。若任务来源变化，界面保留旧输入供核对，并引导回到现行题目。学生在公交或课间完成片段学习时，学习连续性由持久任务和本地输入保护共同支持。
