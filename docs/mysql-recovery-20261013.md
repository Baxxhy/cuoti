# 2026-10-13 本地 MySQL 恢复与启动修复

## 故障和根因

项目原数据目录是 `.mysql-data/`，MySQL 8.0.42 在启动时报告 `MY-013039`：无法创建已存在的 `innodb_undo_001`。在隔离副本中完成恢复和正常关闭后，改回隐藏目录名称仍然复现该错误。

MySQL 的启动表空间扫描会跳过隐藏目录，包含扫描起点。官方 [Bug #95071](https://bugs.mysql.com/bug.php?id=95071) 说明了这一行为；[8.0.42 源码中的 Dir_Walker::walk_posix](https://github.com/mysql/mysql-server/blob/mysql-8.0.42/storage/innobase/os/os0file.cc#L3343) 直接对起始目录执行隐藏目录检查。因此修复使用非隐藏的 `mysql-data/`，保留数据库文件，移除了旧脚本中初始化后移动 UNDO 文件的处理。

## 数据保全证据

- 原服务启动失败且没有活动 PID；恢复工作在独立的 3308 端口进行，期间应用没有启动或写入。
- 完整物理备份保存在 `.mysql-recovery/competition-20261013/original/`；原始目录还完整保留在同级 `failed-original/`。
- 原库全部 193 个文件的尺寸与修改时间和物理备份一致；用户、错题、作答、步骤四张表的数据文件 SHA-256 均一致。
- 恢复副本的 **49 张表全部通过 MySQL CHECK**，包含原有 **63 名用户、88 道错题**。
- 另有仅管理员可读的完整逻辑备份 `minddimension.sql`，以及 49 张表的精确行数清单。备份含学习数据，不纳入 Git，不作为比赛展示材料发布。

## 验证记录

同一数据库整体改名为 `mysql-data/` 后，正常启动成功；再次执行干净关闭和 `scripts/start_mysql.sh` 启动也成功。两次均没有移动或删除 UNDO 文件。迁移后及第二次启动后的 **49 张表精确行数均与逻辑备份清单完全一致**，仍有 63 名用户、88 道错题。随后才允许应用接入验收。

验收生成的独立测试账号和测试错题会使后续总数增长，上述数字是恢复时的原始基线。额外的全新隔离实例在根因确认后关闭，未导入、替换或删除现有学生数据。
