# 任务异常预算与恢复

本批补齐最终智能体规格中的时限、回合、重试和迟到结果门槛，保持仓颉业务/MySQL、Python计算和既有原图/作答边界。

1. 仓颉从worker进入领取开始用单调时钟计时，覆盖上下文准备、计算、重验、学习写入和事务末尾。45秒为提交预算；Python至多38秒、HTTP至多40秒、认知计算至多5秒，且都扣除已耗时间。
2. Python接收仓颉传入的剩余计算预算，只能缩短上限。过期结果、流式读取和事务最后更新后都复核，不把多个阶段的单独上限相加。
3. 达24个计算回合或72次执行尝试后提供明确结束/回原题行动；幂等重放仍可读原回执，新的作答/上传不再受理。
4. 使用真实算法前的本地测试代理验证：超时后有效结果迟到、取消后结果迟到、事务末尾超时整体回滚。代理只用于隔离验收，不进入产品部署。
5. 验证停止路径、恢复与重新开始、原记录保留、不重复计分，再运行完整仓颉浏览器门槛并提交。

单调时钟依据[官方MonoTime示例](https://docs.cangjie-lang.cn/docs/1.0.4/libs/std/time/time_samples/monotime_test.html)。数据库时间继续用于持久租约与记录时间，单次执行的耗时不依赖系统时钟调整。

提交预算是业务安全边界；底层不可立即中断的网络或数据库调用可能延后失败状态可见时间，不能把此设计声称为硬实时SLA。测试按实际受理、失败与迟到响应复核时限，代理记录延迟完成耗时；真实上游性能仍由后续能力验收测量。

## 实际边界

- worker领取前创建45秒单调预算；准备、计算、重验、学习证据、照片步骤绑定及事务末尾共用。预留写入时间，剩余不足时不再发起新的阶段；零超时不会被解释为无限等待。
- `task_budget_ms`是内部算法合同，范围1—38000且拒绝布尔值；只能缩短计算上限。规划器5秒、转写32秒仍在外层剩余时限内，调用超时后不会因为迟到结果补交学习事实。
- 保存检查点后及提交前复核。审计的`native_elapsed_ms`记录领取开始至提交前的已耗时间，不含排队和COMMIT回执等待；原Python `elapsed_ms`和未知usage继续保留。
- 达上限时已在执行的最后一轮仍可合法完成；其后新的答案、求助和上传停止受理。相同请求号重放继续返回原回执，取消始终可用。耗尽重试的租约恢复会结束pending动作，不悬挂。
- 页面提供一个“结束并回原题”主行动，后端确认结束才导航；原任务/原图/尝试保留。本机未提交草稿默认收起，结束后回看旧任务仍可读，不自动带到新任务。
