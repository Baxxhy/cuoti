# 仓颉后端的语言能力与业务边界

目标是让仓颉承担实际业务后端，Python 保留既有专业算法。此文只记录代码已经使用的能力，不将换语言本身视为功能改进，也不声称尚未测试的性能优势。

## 本轮：学习档案、图谱与首页

- `src/cognition_graph.cj` 用 `CognitionKind` 枚举表达知识点、错题、错因和学习策略四类节点。每类的 JSON 标签和展示上限通过枚举方法集中定义；构造节点必须传入枚举值，避免拼错类别导致节点漏显。`CognitionNode` 与 `CognitionEdge` 把节点身份、类别和关联两端保留为明确的业务对象，仅在响应边界转换成 JSON。
- 图谱查找使用 `Option<CognitionNode>`、`Option<JsonObject>` 与模式匹配，显式处理缺失知识卡、缺失题目以及空候选。`connect` 先确认两端节点存在，裁剪可见节点后再次筛选连线，避免返回没有端点的关联。
- 学习统计以 `HashSet` 合并同一学科的相同知识点和规范化错因。复合键使用 JSON 数组编码，允许名称中含分隔符，避免不同字段组合错误合并。统计和首页的去重顺序沿用原版接口约定。
- 查询接口使用仓颉 `try (db = Database.fromEnvironment())` 的 `Resource` 生命周期；读取一组关联数据时使用同一事务，正常结束和异常路径都释放连接。底层 `Database` 继续通过 C FFI 调用 MySQL 官方客户端，并由仓颉绑定 SQL 参数、管理事务；没有 Python 数据库代理。
- 首页根据持久化的会话、复习、掌握度及教师反馈生成继续学习入口，不依赖模型临时描述。统计使用原版 UTC 滚动窗口；首页复习截止和连续学习天数沿用北京时间规则。

## 已有基础能力

- 原生 HTTP 处理、签名鉴权、参数绑定和事务业务由仓颉负责。
- `Resource` 同时管理 MySQL 原生字符串、数据库连接与媒体文件；薄 C 适配器仅提供数据库、密码学和 POSIX 文件原语。
- 教学阶段和证据门槛由仓颉决定，模型返回内容不能自行跳过学习检查。
- 图像处理、Qwen API 池、Pydantic、SymPy 等继续在独立 Python 算法服务执行；这次没有修改原算法、原 Python 后端或前端。

## 验证与尚存边界

`scripts/smoke_cangjie_insights.py` 用真实仓颉 HTTP 服务及隔离 MySQL 验证档案、趋势、知识卡、图谱、首页、权限和教师反馈。它只在测试进程中提取原 Python 只读接口函数，对同一隔离数据逐项比较结果；不启动旧业务后端，不读取原版应用配置。旧接口没有规定相同时间记录的稳定顺序，对照样例使用明确的先后时间。

仓颉业务中仍有较多 JSON 状态对象，尚未实现全领域的静态类型化；本轮的枚举和节点对象是实际落地的部分，不代表整个后端已完成类型重构。路由迁移进度以 `routes.json` 为准。完整迁移、真实模型与前端验收仍需继续完成。

## 教师作用域与时间处理

`school_access.cj` 的 `TeacherScope` 在构造时核对数据库中的真实角色，后续成员访问、班级所有权和审计 actor 均使用同一作用域。`SchoolAction` 枚举同时产生 action 与 target_type，使不同操作不能随意拼接错误的目标类型。所有写操作连同审计在一个仓颉事务内完成；验证已覆盖审计插入失败后的原业务回滚。

复习时间使用仓颉标准库 `std.time.DateTime.parse` 校验日期与时区，再通过 Unix 时间转换成 UTC 数据库时间；无时区输入沿用原 Python 的 UTC 约定。实现依据[仓颉时间 API](https://docs.cangjie-lang.cn/docs/1.0.4/libs/std/time/time_package_api/time_package_structs.html)，并已用当前固定 SDK 编译及真实 HTTP 运行验证。

`smoke_cangjie_school.py` 验证教师/家长权限与业务闭环，并对原 Python 只读接口进行隔离数据库结果对照。教师题库、任务和复核的业务迁移仍需继续。

## 2026-10-16 接口精简

根据实际调用审计删除 9 条空操作、重复或废弃入口。统计以 overview 为唯一入口，账户退出由原有前端本地行为完成。routes.json 现为 94 条有效契约；历史 103 条的去向和直接/间接调用区别见 ROUTE_USAGE.md。测试引用不计为学生页面实际使用，独立能力也不宣称已接入页面。此阶段没有新增运维或部署工作。

## 作业状态与 Python 算法

`SchoolTable` 为允许的落库表提供封闭枚举，`SchoolRecord` 只接受已知列名并绑定所有值，默认值来自开发期生成的 `schema/school_defaults.json`；运行时没有 Python ORM 业务代理。`AssignmentOutcome` 与 `ReviewConclusion` 分别表达待复核/已判定及五类人工结论，其方法集中给出任务与作答状态，避免互相冲突的字符串更新。

认知算法保留在 Python：原 ORM 入口与内部 cognition_update 复用 `cognition_rules.py`。仓颉只组织证据、读取快照、调用计算并在同一 MySQL 事务落库。教学完成与作业判定不再维护两份认知公式，54 组原始结果与 Python 原版回归验证算法未变。模型与数学判题继续走原 Python 能力。

教师决定以服务端任务版本为条件；认知证据、复核记录、旧/新作答状态和审计同事务提交。复核旧提交只完成旧作答，不覆盖学生的新提交。未对外声明并发或性能收益。

## 学习历程的类型与查询边界

`JourneyAction` 枚举封闭定义八种下一步入口，每个分支一起给出名称、URL 和原因，编译器要求覆盖全部枚举值。`buildLearningJourney` 是不访问数据库的业务投影，`learningJourney` 仅负责鉴权及 MySQL 快照查询，方便以原 Python 输出独立验证展示语义。题目归档和用户隔离在读取入口限制，历史数量在 SQL 中限制。它不计算新的掌握度，也不修改算法。

## 复核纠正操作

`ReviewChange` 封闭定义 Revoke、Regrade、Transfer，穷尽分派到独立事务内业务函数并映射为 SchoolAction 审计类型。权限、更新和审计共用同一数据库事务。撤销先锁定记录，按原 Python 的解码后数值比较决定是否恢复，避免 MySQL FLOAT 与绑定参数直接比较时的精度差异；旧提交的状态同步也以 latest_attempt_id 为条件。重判只调用既有 Python 算法，记录原始批改与本次修订证据，避免在仓颉中再实现判题公式。
